\chapter{System Implementation and Application}
\label{chap:ch7}

\section{System Overview}

To demonstrate the models developed in this thesis and allow visual comparison of reconstruction quality across architectural variants, we built an interactive web application. The application allows users to select fractured objects from the Breaking Bad dataset, choose between eleven model variants (baseline, pair attention, double attention, and Gabriel graph filtering, each trained under up to three configurations: two-piece on the reduced subset, two-piece on the full dataset, and multi-piece on the full dataset), run inference, and inspect both the broken fragments and the assembled result in interactive 3D viewers.

\section{Architecture}

The system follows a two-server architecture with a clear separation between presentation and computation (Figure~\ref{fig:app_architecture}).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.9\linewidth]{figures/app_architecture.png}
    \caption{System architecture. The Django server handles user requests and serves static assets. Inference requests are proxied to the FastAPI GPU server when available, with automatic fallback to precomputed results.}
    \label{fig:app_architecture}
\end{figure}

The \textbf{Django web server} (Django 6.0) serves as the main entry point: it renders the user interface, hosts the 3D mesh files (Wavefront OBJ format), and exposes a REST-style JSON API for fracture metadata retrieval and inference orchestration. The \textbf{FastAPI inference server} runs on a separate GPU-equipped machine and performs the full Jigsaw inference pipeline---preprocessing, forward pass, and global alignment---returning the assembled meshes as OBJ text. Input validation rejects requests with invalid piece counts or malformed files.

To ensure the demo functions reliably during presentations without requiring dedicated hardware, the predict endpoint implements a three-tier fallback: live GPU inference when available, precomputed results from a static cache when the GPU is unreachable, and an informative error response otherwise.

The user interface presents a single-page layout with a scrollable narrative column summarizing the thesis and a sticky interactive demo panel. The 3D viewers are built with Three.js, rendering fragment meshes with flat shading and distinct per-piece colors. Each viewer provides orbit controls for rotation, zoom, and pan, with automatic camera fitting. In the input viewer, pieces are scattered outward from their shared centroid to visually separate fragments.

\subsection{Functional Requirements}

The application satisfies the following functional requirements:

\begin{itemize}
    \item \textbf{F1 -- Fracture visualization:} Display broken 3D fragments in an interactive viewer with rotation, zoom, and pan controls.
    \item \textbf{F2 -- Model selection:} Allow the user to choose between eleven model variants covering different architectural configurations, dataset sizes, and piece counts.
    \item \textbf{F3 -- Inference execution:} Perform end-to-end fracture assembly inference (feature extraction, segmentation, matching, and global alignment) given a set of OBJ fragments.
    \item \textbf{F4 -- Result visualization:} Display the assembled object in a separate 3D viewer for inspection.
    \item \textbf{F5 -- Graceful degradation:} Operate without a GPU server by serving precomputed results from a static cache.
    \item \textbf{F6 -- Example browsing:} Provide navigation controls and a fullscreen grid for browsing the complete set of available examples.
\end{itemize}

\section{Software Quality Considerations}

The system is designed around a separation-of-concerns principle: Django handles presentation, dataset browsing, and request orchestration, while FastAPI isolates GPU-based model inference. This separation simplifies testing and deployment, and allows the user interface to remain functional even when live inference is unavailable.

Several validation mechanisms prevent invalid inference requests. On the Django side, user selections are restricted to known dataset examples, model variants, and piece counts. On the FastAPI side, incoming requests are validated for supported model identifiers, piece count limits, decodable OBJ content, and well-formed input data before any inference is executed.

The prediction workflow follows a proxy-and-fallback design: Django acts as a proxy between the user interface and the FastAPI inference server, first attempting live GPU inference, then falling back to precomputed cached outputs if the GPU server is unreachable, and finally returning a structured error response if neither source is available. This ensures the demo never fails silently.

Although the application is a local research demo rather than a production system, basic security measures are included: inference is restricted to predefined examples and supported model variants, request payloads are validated before processing, and browser-facing POST requests are protected through Django's CSRF mechanism.
